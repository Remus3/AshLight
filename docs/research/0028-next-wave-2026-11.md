# 0028 - Next wave of player value (Nov 2026)

Date 2026-11-17. The ROADMAP is nearly drained (research 0020, 0023 rows
done). This note ranks the next wave inside the ToS floor (CLAUDE.md,
decisions 0003, 0004, 0013) using only data AshLight already has: the
user-pasted PoB build and its outputs, the opted-in Client.txt tail, the
per-press item text, and the cached poe.ninja price book (decision 0026).
Floor cases were ruled by the adjudicator on 2026-11-17 (section 6). Top 6
are filed as ROADMAP rows (section 7).

## 1. What PoB already exports (source check)

- A PoB build XML carries `<PlayerStat stat=... value=...>` for every
  displayed stat; the save loop writes each one unconditionally (its
  condFunc test is `(... or true)`): Path of Building PoE2, pinned checkout
  in the AL sidecar cache (config/tc_pins.json), `src/Modules/Build.lua`
  save of `PlayerStat` (read 2026-11-17).
- The displayed set includes `FireResist`, `ColdResist`,
  `LightningResist`, `ChaosResist`, their `*OverCap`, `Str` / `Dex` /
  `Int`, `ReqStr` / `ReqDex` / `ReqInt`, `Spirit`, `SpiritUnreserved`,
  `Life`, `EnergyShield`, `TotalEHP`, `*MaximumHitTaken`,
  `PhysicalDamageReduction`, `EvadeChance`, `EffectiveBlockChance`,
  `NetLifeRegen` (same checkout, `src/Modules/BuildDisplayStats.lua`, read
  2026-11-17).
- PoB itself warns on these: `ReqStr` "You do not meet the Strength
  requirement of ..." when `v > o.Str` (likewise Dex, Int) and
  `SpiritUnreserved` "Your unreserved Spirit is negative" when `v < 0`
  (same file, warnFunc entries, read 2026-11-17).
- AshLight already parses PlayerStat into `BuildModel.stats`
  (server/al/theorycraft/model.py) and uses the resist values against a
  75 cap in the waystone rules (server/al/theorycraft/waystone.py).

So build-health warnings are comparisons of PoB's own numbers to PoB's own
warning conditions and the 75 cap; nothing is recomputed. That keeps them
inside decision 0004 (no own calc engine).

## 2. Build-quality helpers (ranked)

1. Build health card (MATH-BUILD-HEALTH). Uncapped resists (each element
   vs 75, chaos shown as a number not a fail), unmet attribute
   requirement, negative unreserved spirit, weakest element by PoB's
   `*MaximumHitTaken` (argmin). Data: PoB outputs only. Value: high; the
   most common levelling mistake is an uncapped resist after an act
   transition. Floor: ok with condition (section 6 A).
2. "Look for next" per slot (MATH-NEXT-LOOK). Turn the health gaps plus
   the MATH-WEIGHTS stat ranking (already PoB-derived) into one priority
   line per gear slot ("Ring: cold res, then life") and feed the existing
   UTIL-SEARCHSTR builder. Data: PoB outputs + equipped items in the XML.
   Value: high; answers "what do I buy". Floor: ok - ordering existing PoB
   numbers, no formula.
3. Defensive layer checklist. A list of present / absent layers (armour,
   evasion, ES, block, regen) from the same PlayerStat values. Value:
   medium; overlaps item 1, and any "enough" threshold would be an
   AshLight-authored heuristic that can mislead. Folded into item 1 as
   plain values, not filed separately.

Forbidden by decision 0004 (not filed): own EHP, DPS or resist math for a
hypothetical item without PoB (the TC-DELTA path already uses PoB), or a
"needed armour for X hit" calculator.

## 3. Campaign / levelling helpers from Client.txt alone

1. Under-level warning (UTIL-UNDERLEVEL). `Generating level N area` gives
   the area level; level-up lines give the player level (research 0002).
   Show "N levels under this zone" in the act card and the overlay status
   word when the gap is at or above a setting (default 3). No XP-penalty
   formula is shown. Value: high for 1.0 newcomers. Floor: ok (6 B).
2. Personal-best act splits and deaths by zone (UTIL-RUN-HISTORY). Keep a
   small local history of finished campaign runs (act splits, deaths per
   zone) so the act card shows "best" and "delta to best", and a deaths-by-
   zone list across runs. Client.txt can be deleted or trimmed by the player
   (whether the game ever rotates it is UNVERIFIED), and the LIVE-RESUME scan caps at 32 MB (decision
   0008), so a rescan cannot be the source. Value: medium-high for
   re-rollers and league starts. Floor: ok with condition (6 C).
3. Multi-character view. Level-up and death lines name the character;
   splits, pace and deaths could be kept per character. Value: medium;
   most players level one character at a time and the configured-character
   rule (state.py) already picks one. Not filed; revisit after
   UTIL-RUN-HISTORY (it would key that history by character).

## 4. Economy helpers from the cached price book

1. Price watch (UTIL-PRICE-WATCH). The item-check press already prices
   uniques and stackables (PRICE-UNIQUE, PRICE-STACKABLES). Remember the
   last N priced items locally; when the hourly price book refreshes, flag
   any whose price moved past a threshold (default 25 percent) in a
   dashboard list. No new read; no trade call; nothing while web data is
   off. Value: medium-high for anyone holding an item to sell. Floor: ok
   with condition (6 D).
2. "Worth picking up" list. Already covered by the UTIL-FILTER-2 price
   tiers (loot filter) and UTIL-MOVERS. Not filed.

## 5. Quality of life

1. Settings export / import (UX-SETTINGS-IO). Download AshLight's own
   settings on the player's click (decision 0031 / 0034 pattern) and import
   them through a browser file picker with an allow-list schema. Value:
   medium (new PC, reinstall, 1.0 fresh start). Floor: ok with condition
   (6 E).
2. Compact narrow layout (UX-NARROW). A single-column dashboard below
   about 520 px wide, so the dashboard fits a narrow side window or a
   tablet-width browser on the same PC. Value: medium. Floor: ok; the bind
   stays 127.0.0.1.
3. Phone view over the LAN: NOT doable. CLAUDE.md "Bind 127.0.0.1 only ...
   LAN access stays off"; a phone needs a LAN bind. OPERATOR DECISION; not
   filed as a work row (6 F).
